# Draft and polish a complete post

Use the agreed reader, direction, material, and voice. If material is incomplete,
use [gap-resolution.md](gap-resolution.md) while writing supported sections.

## Write the body

Start where the argument needs the most work. Expand notes into the explanation,
evidence, and consequence the reader needs. Introduce concepts before relying on
them. Keep the author's reasoning and sequence unless a change serves a clear
reader need; explain a proposed change to the central argument before applying it.

Choose form for the passage: prose for an argument, lists for parallel items,
tables for comparisons, quotes when wording matters, and code blocks for multi-line
examples. Use callouts only for material that would interrupt the main explanation.
Explain meaningful choices without seeking approval for each sentence.

## Choose supporting art and code

Recommend assets only where they explain something prose alone does not explain
well. A prose-only post is valid. Discuss the purpose and placement of a proposed
asset with the author:

- **Illustration:** explain an idea or establish a relevant scene. Describe its
  content and caption; distinguish illustration from evidence.
- **Diagram:** show relationships, flow, or state.
- **Screenshot:** show actual interface behavior through a real capture.
- **Chart:** show a supported comparison, with data sources and units.
- **Code:** demonstrate the smallest example needed to explain or reproduce the
  point, with its language, inputs, expected behavior, and relevant version.

Track each chosen asset's source or input and status in working notes. Use a
relevant diagram or design skill when producing an agreed asset.

Inspect code before presenting it as actual project behavior. Check library syntax
against current documentation and run examples when the environment supports it.
Label illustrative code and report untested code. Request missing sources or keep
an explicit placeholder; never invent output, screenshots, or measurements.
Planning an asset does not mean it has been delivered.

## Revise the whole post

Check the introduction, title, and ending against the body. Keep them when they
already work. The opening promises what the article delivers, and the ending
follows from its evidence. An unresolved question can be an honest ending.

Read for repeated points, missing steps, contradictions, uneven detail, and changes
in voice. Use [writing-principles.md](writing-principles.md) for relevant editorial
decisions rather than applying a fixed pattern to every paragraph.

Use `unslop` for the full-post cleanup pass, preserving the requested voice and
scope. Supply `VOICE.md` and relevant author samples when available. For David,
also read unslop's `references/author-patterns.md`. Keep deliberate quirks, asides,
and useful repetition. Judge changes against the source rather than an AI-detector
score.

Check that required assets are delivered or explicitly waived, and report missing
evidence or verification. If material gaps remain, return a partial draft with
those gaps visible. An empty question list alone does not prove completion.
